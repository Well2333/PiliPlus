# VideoTogether 兼容实现约定

本文档约束 PiliPlus 的 VideoTogether 兼容功能。修改协议、播放器接入或房间生命周期时，
必须同步更新本文档和对应测试。

## 兼容目标

- 以 `VideoTogether/VideoTogether` 官方 Go 服务端和浏览器客户端的当前协议为准。
- 默认服务地址为 `https://vt.panghair.com:5000`，用户可以在设置中覆盖。
- 服务地址只允许 `http` 或 `https`；WebSocket 分别映射为 `ws` 或 `wss`，路径为
  `/ws?language=zh-cn`。
- 首版兼容范围包括创建/加入房间、控制端状态上报、成员状态上报、视频地址跳转、
  播放/暂停/进度/倍速同步和文字消息。
- 语音通话、EasyShare、M3U8 内容中继和真实媒体地址代理不属于首版范围；未知消息必须忽略，
  不能导致会话断开。

## 协议约定

WebSocket 消息均为以下 JSON 外层结构：

```json
{
  "method": "/room/join",
  "data": {}
}
```

必须支持的客户端请求：

- `/room/update`：房主创建或更新房间；
- `/room/join`：成员加入房间；
- `/room/update_member`：成员上报加载状态和当前页面；
- `send_txtmsg`：发送文字消息。

必须处理的服务端消息：

- `/room/update`、`/room/join`、`/room/update_member`：更新本地房间快照；
- `replay_timestamp`：校正本地与服务端的时钟差；
- `send_txtmsg`：接收文字消息；
- 带 `errorMessage` 的消息：展示错误，但仅在创建/加入失败时结束启动流程。

官方服务端不广播成员清单、昵称、`tempUser` 或 `/room/update_member.userId`；官方浏览器插件把
`send_txtmsg.id` 当作单条消息 ID，并不存在昵称协议。PiliPlus 只能在开启“在昵称后添加 [piliplus]”时，
把会话唯一 ID 和 `[piliplus]` 后缀编码进真实文字消息的 `id` 字段；本端展示和昵称设置必须隐藏内部唯一
ID，昵称设置同时不得显示或重复保存后缀。禁止为探测能力自动发送空消息或伪造聊天，因为官方插件会弹出
“有新消息”并可能初始化语音。其他 PiliPlus 成员只在真实消息携带有效后缀后计入已识别人数；未发消息、
标识关闭或身份未知的成员一律按非 PiliPlus 处理。成员总数变化时必须清空旧识别集合并重新登记本机，避免
离房成员残留造成误判。

官方服务端的 `/room/update` 同一时刻只允许一个 `tempUser` 写入。PiliPlus 默认在客户端层实现
“最后本地操作者接管”：跟随端检测到本地播放、暂停、拖动、倍速或视频切换后，使用新的
`tempUser` 接管服务端写权。旧控制端收到其他控制端的更新或“其他房主正在同步”后，必须立即降级为
跟随状态；发生写权冲突时还要断开原 WebSocket、新建连接并以成员身份重新加入。不得让所有客户端
持续调用 `/room/update`，否则会反复抢占写权。

“双向同步控制”关闭时进入官方兼容模式：通过“加入房间”进入的普通成员不得因本地播放器操作调用
`/room/update`，只能跟随房间状态；成员仍可通过 `/room/update_member` 上报缓冲状态。通过“创建房间”
进入的创建者维持控制能力，被其他人接管后自动跟随，之后发生新的本地操作时可以用新 `tempUser` 重新
取得写权。当前显示角色和“是否曾持有控制权”的恢复资格必须分别保存：被接管时显示成员，重新取得写权
后再显示房主。

当“双向同步控制”关闭但服务端 `memberCount` 大于零，且本机已通过会话后缀识别的唯一客户端数与
`memberCount` 完全相等时，可以自动绕过官方兼容模式并允许双向接管。人数不足、超出、未知或昵称标识
关闭时必须继续兼容模式；不得用“房间里出现过一个 PiliPlus”推断全部成员都是 PiliPlus。该判断是保守的
被动能力协商：其他客户端尚未发送真实文字消息时，保持只跟随属于预期降级而不是同步故障。

会话每 400 毫秒观测播放器以及时发现本地操作；只有当前控制端每约 2 秒上报房间状态，跟随端
每约 2 秒上报加载状态。服务端正式配置会清理三分钟未更新的房间，因此控制端不能只在用户操作时上报。
WebSocket 收到播放状态后必须立即应用；应用上一状态期间收到的新状态应合并为“仅保留最新状态”，不能
直接丢弃并等待下一次心跳。
每个房间会话和 WebSocket 连接都必须使用单调递增的代际标识。所有异步回调、播放器命令、导航和重连在
每次 `await` 后都要确认仍属于当前代际；离开房间必须先使代际失效，再等待资源释放。旧连接的消息、关闭
通知和旧房间任务不得改变新会话。WebSocket 建立仅代表传输可用，重连必须等 `/room/join` 权威快照应用
完成后才恢复心跳或写房间；重连期间的新请求合并处理，不能静默丢弃。
跟随端按房间修订号执行单一 latest-wins 队列：慢速播放器操作期间的新状态替换待执行状态，旧修订完成后
不得上报成员成功或覆盖新状态。播放器准备/恢复失败只影响本轮播放同步，不得主动拆掉健康 WebSocket。
首次绑定播放器以及远端从暂停切换为播放时，必须主动下发一次播放命令，不能只依赖播放器 UI 层的缓存
状态判断。后续同步以底层播放器的实际播放状态为准；实际状态与房间状态不一致时应重试对应命令。
播放适配器必须在视频页建立后立即绑定，不能等到底层 Player 创建完成。关闭自动播放、页面仍显示封面时，
若远端房间进入播放态，应先通过页面注入的准备回调创建 Player 并开始拉流，再校正倍速、进度和播放状态；
播放地址仍在请求时允许本轮准备失败，但后续轮询必须继续重试。远端房间保持暂停时不得仅为同步而提前拉流。

服务端时钟偏移采用与官方客户端等价的四时间戳计算：

```text
offset = ((serverReceive - localSend) + (serverSend - localReceive)) / 2
```

播放中的目标进度为：

```text
room.currentTime + (serverNow - room.lastUpdateClientTime) * room.playbackRate
```

暂停时直接使用 `room.currentTime`。

播放中的默认进度校正阈值为 0.5 秒；用户配置的阈值只作用于播放中。房间暂停或因成员缓冲而临时等待时
使用固定 0.1 秒阈值并以 `room.currentTime` 对齐，不能继续投影前进。

加入房间和本端 `/room/update` 确认包中的 `timestamp` 必须结合请求往返中点立即初始化时钟偏移；
之后再用 `replay_timestamp` 的四时间戳结果精化。等待 `/room/update` 确认时，只能用
`lastUpdateClientTime` 与当前请求一致的广播完成 Future，其他客户端的广播不得误完成本地请求。

## 分层与依赖

- 协议模型和 URL/时间计算必须是可单元测试的纯 Dart 逻辑。
- WebSocket 客户端只负责传输和消息解析，不依赖 Flutter 页面或具体播放器。
- 会话服务只依赖抽象播放接口；`PlPlayerController` 通过单独适配器接入。
- 页面导航以回调注入会话服务，服务层不得直接依赖 PiliPlus 路由实现。
- 普通播放流程不依赖房间服务；未加入房间时，同步逻辑必须无副作用。
- 远端播放命令必须在异步操作开始前和结束后标记本地变化抑制区间；播放器 `seek` 返回的 Future 必须在
  实际 seek 完成（或被更新的 seek 明确取代）后才完成，防止远端命令被误判成本地抢控。
- 底层 Player 换源必须串行执行并携带媒体代际。新换源请求到达即使旧请求失效；旧 `open` 返回后不得触发
  自动播放或初始化回调，队列最终必须以最新媒体收敛。等待 duration 的 seek 必须有超时并校验 Player 与
  媒体代际，换源后不得把旧进度应用到新视频。

## 视频标识与跳转

- 投稿视频使用 `https://www.bilibili.com/video/<bvid>?p=<part>`；第一 P 可以省略 `p=1`。
- PGC 视频优先使用 `https://www.bilibili.com/bangumi/play/ep<epId>`。
- 判断是否为同一视频时比较 BV 号和分 P，或比较 epId；忽略来源跟踪参数和
  `VideoTogether*` 状态参数。
- 成员加入房间后可以按设置自动打开房主 URL。PiliPlus 无法处理的非 B 站页面只提示用户，
  不交给内置 WebView 冒充原生播放器同步。

## 设置与敏感数据

- 服务器地址、显示名称、是否添加 `[piliplus]` 后缀、自动跳转、倍速同步、双向同步控制、等待成员缓冲、
  密码保护、进度校正阈值和“未加入房间时隐藏”
  存入现有 `setting` Hive box，并随现有设置导出/导入。
- “在昵称后添加 [piliplus]”和“未加入房间时隐藏”默认开启。前者关闭后不发送身份标识、不显示
  PiliPlus 用户数，也不得因其他成员的后缀自动绕过兼容模式。
- 房间密码只保存在当前内存会话中，不写入持久化存储或日志。
- 切换服务器地址只影响下一次加入/创建；活动会话不会静默迁移服务器。
- 在线投稿和番剧的视频简介操作栏必须把“一起看”放在分享按钮右侧，不再放入右上角播放器菜单；本地
  文件不显示该入口。开启“未加入房间时隐藏”后，未入房时隐藏操作栏入口，加入房间后无条件强制显示。
- 开启昵称标识时，房间界面在“在线成员：x”后显示“（PiliPlus 用户：y）”；`y` 只统计当前成员数周期
  内本机及通过真实文字消息确认的唯一 PiliPlus 会话，不得把推测值显示成已识别人数。

## 成员缓冲等待

- 官方当前协议仍支持成员通过 `/room/update_member.isLoadding` 上报缓冲，服务端将在线且位于同一页面的
  任一成员缓冲状态聚合为 `room.waitForLoadding`。
- 启用“等待成员缓冲”时，控制端收到等待状态变化后应立即处理，不能等到约 2 秒的普通心跳；控制端和
  未卡顿成员暂时暂停，正在卡顿的成员保持播放请求以继续加载。
- 等待缓冲属于临时传输反馈，不是用户主动暂停。控制端物理暂停期间仍应向房间发布 `paused=false`；等待
  解除后自动恢复。不得把该机制当作普通成员任意播放控制，它只能温和地请求全体等待加载。

## 生命周期

- 房间会话独立于房间页面存在，跳转到视频页后继续同步。
- 播放器未就绪时允许先创建或加入房间；视频页应先绑定可准备的播放适配器。当前房间正在播放时，由远端
  状态触发播放器初始化；当前房间暂停时保持封面和未拉流状态。
- 离开房间、创建/加入失败或应用退出时必须停止计时器并关闭 WebSocket。
- 普通后台状态必须暂停会话轮询和本地操作检测，不能把系统自动暂停误判成用户暂停或抢控。恢复前台时
  必须废弃旧 WebSocket，先重新加入并拉取最新房间状态、校正播放器，再由原控制端尝试恢复写权；
  若写权已被接管则自动保持成员身份。
- Android/桌面小窗和用户明确启用的后台播放仍视为活动播放：不得因 paused 生命周期事件暂停 Player，
  VideoTogether 会话继续同步；离开小窗或系统实际冻结后仍由消息新鲜度检查补偿。
- “支持/允许自动进入 PiP”只是能力配置，不能永久当作“当前正在 PiP”；后台豁免只依据真实 PiP 状态、
  明确启用的后台播放，或最长 3 秒的自动 PiP 过渡窗口。窗口结束仍未收到真实 PiP 状态就按普通后台暂停；
  真实状态迟到时要解除挂起、重连并按房间权威状态恢复。播放器只允许在 `resumed` 生命周期恢复，
  `inactive` 不能触发误恢复；页面路由导致的自动暂停也必须进入本地变化抑制区间。返回视频页时不得沿用
  覆盖页打开前的播放状态，必须以当前房间状态决定是否起播。
- 移动网络类型变化或从无网络恢复时必须关闭旧连接并立即重连；连接建立后连续 8 秒没有收到任何服务端
  消息视为半开连接。消息静默时长和重连退避必须使用单调时钟；明确无网络时禁止定时器反复连接。失败
  重连采用 1、2、4、8、15 秒封顶退避，网络恢复和前台恢复可以绕过一次退避。
- 每次重连必须重新 /room/join 获取权威房间快照。播放中的既有 Player 需重开当前媒体流并随后校正
  播放/暂停和进度；暂停房间不得仅因重连而启动或重开流。
- 不得同时创建多个 WebSocket、并发应用多个远端状态，或在恢复权威状态前用后台期间的本地快照覆盖房间。
- 播放器解绑后必须保留最近媒体身份但视为未就绪；远端仍在同一视频时允许重建播放器。远端媒体导航和
  播放地址查询都使用 latest-wins 代际，旧请求完成不得把旧流标成当前流；导航未完成可短时去重，但超时
  后必须允许重试，不能永久卡在封面或旧视频。

## 验证

- 对消息编码、房间解析、WebSocket URI、服务器时钟偏移、目标进度和 B 站媒体标识比较
  编写纯逻辑单元测试。
- 本地操作检测必须覆盖自然进度、播放/暂停、拖动、倍速和缓冲转换。
- 能力识别测试必须覆盖昵称后缀编码、设置框后缀清理、内部会话 ID 隐藏、重复昵称的唯一计数、成员数变化
  后清空，以及只有全部成员均确认时才绕过兼容模式。
- 入口策略测试必须覆盖默认未入房隐藏、用户关闭隐藏后常显，以及入房后不受隐藏设置影响。
- 远端状态应用测试必须覆盖底层 Player 尚未创建、播放地址仍在加载以及暂停房间不应提前拉流。
- 稳定性测试必须覆盖消息超时判定、重连退避、普通后台与 PiP 分流、重连后播放流恢复及暂停态不误拉流。
- 竞态测试必须覆盖连接握手期间离开、旧 WebSocket 迟到事件、重连请求合并、延迟 seek 的远端命令抑制，
  以及旧媒体请求被新请求取代；测试通道必须验证资源关闭所有权。
- 前后台和网络恢复必须先应用服务端权威快照，再允许检测新的本地控制操作。
- 每次修改后执行 Dart 格式化、相关单元测试和静态分析。
- 双客户端真实联调至少覆盖：创建/加入、A→B→A 控制权交接、自动打开同一视频、播放/暂停、拖动、倍速、
  切换分 P/剧集、断线重连和离开房间；无法自动完成的项目写入待测报告。

## Fork Android 分发约定

- fork 的无 tag CI 产物使用 `com.example.piliplus.dev.ci`，带 tag Release 使用
  `com.example.piliplus.dev`，两者可与官方 `com.example.piliplus` 并存。
- CI 和 Release 使用同一套 fork 开发证书，但因包名不同仍是两条独立升级链。
- 证书从 `SIGN_KEYSTORE_BASE64`、`KEYSTORE_PASSWORD`、`KEY_ALIAS` 和 `KEY_PASSWORD`
  GitHub Actions Secrets 注入；私钥和口令禁止提交。
- 本地忽略文件 `android/app/key.jks` 和 `android/key.properties` 是唯一等价备份，应离线保存。
